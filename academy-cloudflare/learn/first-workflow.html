FREE LAB 01 / AUTOMATION FUNDAMENTALS

Build a lead router.
Then prove it works.

Learn the engineering discipline behind a basic business automation: defining inputs, validating data, routing requests and testing different outcomes. Start with plain business rules before introducing an AI model.

Level: BeginnerMode: Browser simulation + optional n8n buildData: Synthetic only
Evidence boundary: This is an original training simulation inspired by common lead-qualification design patterns, not a copy of a private course recording or an export from a live client system. It does not collect, transmit or persist form responses.
01 / BEFORE

Define the problem and success criteria

A service business receives enquiries with inconsistent details. Staff must decide which to prioritize. Our goal is to turn those enquiries into predictable routing outcomes, not to pretend that an LLM's response is always correct.

Input contract

Lead ID, service, budget in euros, deadline in days, and contact consent.

Output contract

Exactly one routing decision: invalid, do_not_contact, human_review, priority, standard or nurture.

Acceptance criteria

Identical inputs produce identical decisions; invalid data never creates an outbound action.

03 / CONTROL

Understand the routing rules

OrderConditionDecision
1Malformed ID, budget or timelineinvalid
2No contact consentdo_not_contact
3Requested service not recognizedhuman_review
4Timeline ≤ 7 days AND budget ≥ €1,000priority
5Budget ≥ €500standard
6Otherwisenurture

These thresholds are illustrative business requirements, not recommended pricing or a universal sales policy.

04 / AFTER

Test it, don't just demonstrate it

Download the six synthetic test scenarios (JSON). Build the same rules inside n8n or another workflow tool. Test each route and record the observed result against its expected result.

Test coverage

Priority, standard, nurture, invalid, no-consent and human-review routes.

Failure handling

Make malformed inputs explicit. Never silently label uncertain data as a negative response.

Repeatability

Run the same fixture twice. Discuss how a unique lead ID would prevent duplicate external actions.

Evidence

Capture the workflow diagram and each outcome. Explain one rejected input and one boundary condition.

05 / APPLICATION

Create a client-style deliverable

Write a short handover document: the customer's problem, an architecture diagram, accepted inputs, decision table, test evidence, privacy safeguards and the limitations of your simulation. Do not claim production deployment without authenticated triggers, persistent deduplication, permission checks, monitored failures and real integration tests.

Next challenge: Replace the simulated result with a write to a test-only datastore, use synthetic contact records, and prevent duplicate writes with a unique identifier. Document exactly how you tested it.
